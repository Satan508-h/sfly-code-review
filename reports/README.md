# 评测报告

每一份都是 `python tasks.py eval` 的产物。文件名里的 7 位十六进制是**生成时的代码版本**，
第二行会写明生成时工作区干不干净 —— **只有标着「干净」的那份，数字才精确对应它标注的
commit**。

评测集始终是同一批 30 个用例（15 条手写注入 / 10 条回退真实 CVE / 5 条干净代码），
所以同一层的不同 sha，是**同一份考卷、不同版本的代码**的成绩单。

## 两层量的是不同的东西 —— 引用任何数字之前先问「这是哪一层」

| | 离线层 | 真实层 |
|---|---|---|
| 执行者 | Mock（确定性正则扫描器） | 真实模型 |
| 量什么 | **聚合层**：聚类、去重、置信度闸、冲突消解 | **模型的审查能力**（同时也覆盖聚合层） |
| 代价 | $0 · 秒级 · 可复现 | 约 $0.15 · 10 分钟 · **不可复现**（模型版本和温度都会让数字漂） |
| 能进 CI | 能 | 不能 |

三件不这样读就会读错的事：

* **「精确率 80%」单独说是错的。** 必须带上「离线层 / 注入组 / 聚合层」。
  干净组的误报率主要由扫描器**一次只看一行**的粗糙程度决定，不是系统的精确率。
* **离线层的消融读不出 Worker 数量的差别。** Mock 按 lane 过滤，三份并集
  天然等于一次全报 —— 那一层里「1 个 Worker」和「3 个 Worker」必然同分。
* **两层的阈值扫描结论是相反的**（离线层说 0.30 更好，真实层说 0.35 支配它）。
  这不是 bug，正是必须跑两层的原因：Mock 的置信度是手写常数，
  拿一批错误的分布去定一个读模型自报值的门槛，只会调出一个错的数。

## 真实层那两份，对应的不是当前代码

`a010ba9` / `e9aafd0` 跑于 2026-09-26。**那之后 LLM 层改过 443 行**
（推理预算、空响应判据、成本闸），而两处改动都只会让结果**变好**：

* 截断的响应以前会被判成「未发现问题」，现在不会 —— 以前会白丢发现
* 推理模型以前会把输出预算整个用在思维链上，正文一个字没写

所以那批数字**偏保守**。要让它精确对应当前代码，就重跑一次：
`python tasks.py eval --real`（约 $0.15 / 10 分钟）。

## 其余 20 份是历史快照

每次改代码重跑 eval 都会生成一对新文件（`-offline` + `-ablation-offline`），
**旧的不会被覆盖** —— 这是有意的：两层在同一个 commit 上并存，靠的就是文件名里的
层名（只按 sha 命名的话，后跑的那次会盖掉先跑的）。

代价是中间过程也留在这里。**而它们的数字是重复的**：现存 11 份离线层报告，
精确率 / 召回率全都是 80.0% / 60.6%（逐份核过）—— 因为 M10 的改动落在传输层、
部署配置和前端，没有一条碰到聚合层。
