# 演示脚本

这个项目**没有公网地址**（原因见 [部署手册](DEPLOY.md) 开头），所以演示是
「本地跑起来 + 屏幕共享 / 录屏」。这其实不吃亏：**只有在本地才能演示
`--scale` 和杀掉 Worker 看降级** —— 单容器的精简模式根本演不了这两件事，
而它们恰好是这个项目最值得讲的部分。

---

## 录屏之前：一次彩排（约 5 分钟）

```bash
python tasks.py up          # 七个容器起来，阻塞到健康检查通过（第一次要几分钟构建）
python tasks.py ps          # 全绿再往下走
python tasks.py demo        # 投一次审查，等它跑完（Mock LLM，$0）
```

然后打开 <http://localhost:5173>，确认：

- 运行记录页有一条刚跑完的记录，点进去能看到 **发现 / 实时时间线 / 冲突与成本** 三个标签页
- 顶栏右上角是绿点，写着「完整模式 · redis · mock」

彩排完把数据清掉，录的时候从干净状态开始：

```bash
python tasks.py clean && python tasks.py up
```

> **`durable` 提醒**：`clean` 会删数据卷 —— 只删这个项目的，不影响别的容器。

---

## 录屏脚本（3 分钟左右，七段）

每一段都写清「你做什么 / 你看到什么 / 你说什么」。**说什么是提示，不是台词** ——
照着自己的话讲更自然。

### ① 开场（20 秒）

**做**：停在运行记录页。
**说**：一句话讲清是什么 —— 「GitHub 上一个 PR 提上来，三个专业 Agent 并行审，
主 Agent 汇总去重定级，最后把结论作为评论写回那个 PR。不依赖 K8s，也不依赖 Kafka。」

**不要**一开始就讲架构图。先把「它是什么」说清楚，面试官才有耐心听细节。

### ② 投一次审查，看它自己跑（40 秒）

**做**：

```bash
python tasks.py demo
```

**看**：页面上几秒内自己多出一行，状态从「排队中」一路变到「已发布」。

**说**：「注意这一行是**自己冒出来的** —— 页面开着一条 SSE 流，后端每推进一步
就往前端推一条事件。点进去看时间线。」

**看**：详情页的实时时间线 —— `run.created` → `plan` → 三个 `worker.dispatched`
→ 三条 `worker.result` → `aggregate.done` → `finalize` → `publish.done`。

**说**：「三个 Worker 是真正并行消费的，各自一条 Redis Streams 消费者组。」

### ③ 去重和置信度（30 秒）

**做**：切到「冲突与成本」标签页，指出某条发现的**来源标签**。

**说**：「三个 Worker 独立报出同一处问题的时候，那条发现的置信度会被抬高 ——
这是多 Agent 这个设计唯一能产出、而单 Agent 拿不到的东西。反过来，单条声称
的置信度会被**压低**：模型自报的 confidence 系统性偏高，我们只给它 55% 的权重。」

### ④ 分布式能力：水平扩展（30 秒）

**做**：

```bash
python tasks.py scale 3
docker compose logs -f worker-security | grep "consumer group"
```

**说**：「同一个消费者组，三个副本抢同一个流的消息 —— 这是 Redis 消费者组的
定义，不需要应用层写任何协调代码。`docker compose up --scale` 就行。」

> 这一条**线上演示不了**：公网托管跑的是单容器精简模式，没有第二个进程可以
> 加入消费者组。这是本地演示的第一个不可替代之处。

### ⑤ 容错：杀掉一个 Worker（40 秒）—— **最好的一段**

**做**：

```bash
python tasks.py kill-worker     # 杀掉一个正在跑的 Worker
python tasks.py demo            # 再投一次
```

**看**：run **照样跑完**，但页面上多一个**降级徽章**，写着「降级运行 —— 1 个
Worker 未上报」。

**说**：「Worker 猝死之后，那条消息留在待确认队列里，被同伴回收、重跑；
等重试用完还没有结果，那个 Worker 会**主动补发一条失败结果**再确认 ——
所以屏障能闭合，run 不会挂到超时。报告上会明确标出哪一路没产出结果。」

**这一段值得慢讲**：它把「失败也是结果」这条设计讲成了看得见的东西。

### ⑥ 断点恢复（30 秒，可选）

**做**：

```bash
python tasks.py replay-bootstrap --task-id <刚才那个> --simulate-crash
```

**说**：「图在等 Worker 的时候是**挂起**的，进程里没有它的执行栈。恢复靠的是
一条 SQL 查询（`review_runs` 上的 `status` + `deadline_at`），不是内存里的定时器 ——
所以编排器崩溃重启之后，那些 run 会被扫描器捞回来继续跑。」

### ⑦ 收尾：评测数字（20 秒）

**做**：打开 `reports/` 里那两份真实层报告。

**说**：「这些数字是花真钱跑出来的。最值得看的是这个：**10 条回退真实 CVE
修复的用例，真实模型全部找了出来**（召回 100%），而同一批用例在离线层
一条都认不出来。还有消融：**三个 Worker 比单 Agent 多召回 12.1 个百分点**，
代价是 2.4 倍成本。」

## 被追问时怎么答

这几条是面试官最可能问的，答案都在仓库里，**重点是给出「我量过」而不是「我觉得」**。

| 问 | 一句话答 | 证据在哪 |
|---|---|---|
| 「为什么不用 Kafka / K8s？」 | 这个体量用不上，而且**换掉它们不影响任何业务代码** —— 队列和锁都是协议，两种实现（Redis / 进程内）共用同一份契约测试 | `tests/contracts/`；`python tasks.py test-int` |
| 「怎么保证不重复审查？」 | 靠数据库唯一约束，**不靠 Redis SETNX**（它会过期、会随重启丢失）。SETNX 只是省 token 的快路径 | `worker_results` 的主键；README 的「幂等」那段 |
| 「去重为什么不用 embedding？」 | 确定性、可复现（评测需要它）、无模型下载、微秒级 | `aggregate/cluster.py` |
| 「多 Agent 到底比单 Agent 强多少？」 | **真实模型上 +12.1 个百分点召回，代价 2.4 倍成本**。而且这个结论**离线层给不出来**（Mock 按 lane 过滤，三份并集天然等于一次全报） | `reports/*-ablation-real-*.md` |
| 「置信度阈值 0.35 怎么定的？」 | 扫描出来的，而且**两层结论相反**：离线层说 0.30 更好，真实层说 0.35 支配它 —— 因为 Mock 的置信度是手写常数，拿错误的分布调参数 | `reports/*-real-*.md` 的扫描表 |
| 「部署了吗？」 | **没有，而且原因不在代码** —— 三个平台的原文报错我都留着：Render 要绑卡、HF 的 Docker Space 要 PRO 订阅且国内打不开、vercel.app 被墙。部署配置是完整可执行的，每一步的字段名都实测过 | [`docs/DEPLOY.md`](DEPLOY.md) 开头 |
| 「这项目最难的地方是哪？」 | 「都不报错」那一类。最好举例：一次推理模型把输出预算全用在思维链上、正文一个字没写，而报告会以**「未发现问题」**发布出去 —— 上游看到的现象只是「解析不出 JSON」 | README 的 M10 那节 |

> **「部署了吗」这一问要用上面那个答法**：先说结论（没有），再说原因（平台政策，
> 不是我做不到），最后给证据（`docs/DEPLOY.md` 里记着三个平台的原文报错，
> 以及「跟着平台走的四个数」那张表）。**主动说出限制比被问出来强得多** ——
> 这个仓库的 README 里专门有一节「已知限制」就是干这个的。
